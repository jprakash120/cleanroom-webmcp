# Cleanroom

**A browser-native workspace where an analyst and an AI agent investigate sensitive datasets together — without the raw file ever leaving the browser.**

Built for the [OpenAI WebMCP Challenge](https://openai.com/webmcp-challenge/). Runs entirely client-side on [WebMCP](https://github.com/webmachinelearning/webmcp) + [DuckDB-WASM](https://duckdb.org/docs/api/wasm/overview). No backend, no data upload, no server-side inference.

**Live app:** https://cleanroom-webmcp.jayaprakashjjjjj.workers.dev
**Repo:** https://github.com/jprakash120/cleanroom-webmcp

---

## The problem

Analysts can't safely hand confidential data to an AI agent. Customer records, operator-level production data, financials — the moment that data goes to a model endpoint, it has left your control. So the most useful thing an agent could do (explore the messy, sensitive table with you) is the one thing you can't let it do.

Cleanroom changes the terms. The dataset is loaded into DuckDB compiled to WebAssembly and stays inside the browser tab. The agent works the *same page* you do — but it never receives the raw file. Instead, three kinds of information can cross a visible **disclosure boundary**, each on different terms, and every crossing is logged.

## What crosses the boundary

| Tier | What the agent receives | On what terms |
| --- | --- | --- |
| **Metadata** | schema, column names, row *counts* | flows freely — no cell values |
| **Aggregates** | grouped statistics (`sum`, `avg`, counts…) | only above a **k-anonymity floor** (k = 5) so a group can never describe one person |
| **Raw rows** | individual records | **never** without an explicit human click in the disclosure dialog |

Every disclosure — auto-approved aggregate, human-approved sample, or denied request — is written to a live audit ledger. A reviewer can reconstruct exactly what left the browser and why.

> This is the honest version of the privacy claim. It is **not** "no data ever leaves the browser" — approved results do reach the agent. It is: *the raw file stays local, and only bounded, explicitly governed results ever cross, with a full audit trail.*

## Why this isn't just another DuckDB explorer

OpenAI's own showcase already includes **Duckboard**, an in-browser DuckDB-WASM data canvas. A generic SQL-in-the-browser tool would be a clone of the reference app. Cleanroom is built around the thing plain MCP and a background data tool *can't* do: **real-time, co-present, governed collaboration on sensitive data.** The differentiators are the disclosure gate, the k-anonymity floor on aggregates, the reproducible hypothesis ledger, and the human-in-the-loop correction — not the SQL engine.

## The demo scenario

The bundled synthetic dataset (`data/production_runs.csv`, generated by `data/generate_data.py`) is beverage-manufacturing production runs with a deliberate, discoverable root-cause story:

- **Symptom:** overall output is down (~93% attainment) and looks worst on the C (night) shift.
- **Trap:** a naive "downtime → low output" cut blames the night shift and individual operators, because planned-maintenance downtime is mixed in.
- **Truth:** once planned maintenance is excluded, the real driver is a **filler-pressure fault on LINE-2 during the C shift** over a two-week window (low `filler_pressure_psi` → filler jams → lost units). It's an equipment problem, not a people problem.

`operator_id` is marked sensitive. Grouping LINE-2 / C-shift by `operator_id` alone does not trigger suppression — each operator has 11–16 runs on their own. Adding `downtime_reason` creates smaller operator-by-reason cells: 3 groups meet the k=5 floor while 16 are withheld — forcing the disclosure gate to do its job on camera.

A full investigation walkthrough is in [`docs/DEMO_SCRIPT.md`](docs/DEMO_SCRIPT.md).

## The WebMCP tools

The page exposes seven tools to the agent. Two obvious getters were deliberately *not* built: no `getSelectedRows` (it would bypass the gate) and no `summarizeResult` (the agent can summarize returned data itself).

| Tool | What it does | Privacy posture |
| --- | --- | --- |
| `getWorkspaceContext` | schema, active SQL, selection count, hypotheses | metadata only |
| `executeLocalQuery` | runs read-only SQL, shows results to the analyst | returns **columns + row count only** |
| `getAggregateResult` | grouped stats from named dimensions/metrics | k-anonymous (`HAVING count(*) >= 5`) |
| `requestRows` | asks to share raw records | routes through the **human approval dialog** |
| `addHypothesis` | creates a visible hypothesis card | — |
| `updateHypothesis` | attaches evidence + SQL, sets status, records corrections | — |
| `exportInvestigation` | reproducible report: findings, SQL, full disclosure ledger | — |

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the tool contracts and the request/response shapes.

**Known edge case:** `requestRows` stays pending while the analyst considers the disclosure dialog. Some agent hosts impose their own timeout on a single tool call and may give up while waiting on a human decision. The decision is still recorded correctly in the local ledger either way, but if the host has already given up, the caller may not receive the approved rows on that turn. Approving promptly (a few seconds) avoids this in practice. A future two-step request/result flow would remove this host-timeout coupling entirely — see Roadmap below.

## Run it locally

WebMCP needs a **secure context**. `https://` in production, but `http://localhost` gets a pass for development. ES modules and the sample-data fetch also need a real server (not `file://`).

```bash
# from the repo root — any static server works
python -m http.server 8000
# then open http://localhost:8000
```

Alternatives: `npx serve .` (Node) or the VS Code "Live Server" extension. On Windows PowerShell, `python -m http.server 8000` works the same way.

The app is fully usable by a human on its own — load the sample data and run queries. The agent tools only light up in an agent-capable browser (below).

## Test it with an agent

**ChatGPT desktop app.** Open your deployed `https://` site in the app's built-in browser and enable **site tools** for the page. Free ChatGPT accounts support this; some enterprise/edu account types do not expose the toggle yet. Then ask the agent to investigate — start with *"Read the workspace context and profile this dataset."*

**Chrome (Experimental Web Platform Features).** Chrome ships `navigator.modelContext` behind a flag: go to `chrome://flags`, enable **Experimental Web Platform Features**, relaunch, and drive it with Chrome's built-in agent. For a browser without native support, load the [`@mcp-b/global`](https://www.npmjs.com/package/@mcp-b/global) polyfill before `js/app.js`.

WebMCP is a moving W3C draft — the getter has been both `navigator.modelContext` and `document.modelContext`, and the tool callback is `execute` in some versions and `handler` in others. `js/webmcp.js` is a compatibility shim that detects what's present and registers under every shape, so the app keeps working across hosts as the spec shifts. The status chips in the top bar show which surface was detected.

## Deploy

Static site, HTTPS required. The repo ships config for three sponsors' hosts, each setting cross-origin isolation so DuckDB-WASM can use its faster multi-threaded build:

- **Cloudflare Pages / Netlify** — headers in [`_headers`](_headers) (+ [`netlify.toml`](netlify.toml))
- **Vercel** — headers in [`vercel.json`](vercel.json)

Point any of them at this repo with no build command and an output directory of `.`. If DuckDB ever fails to load on your host, remove the `Cross-Origin-Embedder-Policy` line — the app falls back to the single-threaded build, which needs no isolation.

## Architecture

```
index.html            three-column shell: local data · workspace · disclosure boundary
css/styles.css        the "cleanroom" design system
js/
  webmcp.js           compatibility shim over the WebMCP browser API
  db.js               DuckDB-WASM engine + the read-only SQL guardrail
  privacy.js          the disclosure boundary: sensitivity, k-anonymity, gate, ledger
  hypotheses.js       the reproducible hypothesis / evidence model
  tools.js            the seven WebMCP tool definitions
  state.js            shared workspace state between UI and tools
  app.js              the human's side: grid, selection, modal, rendering, boot
data/
  generate_data.py    synthetic dataset generator (self-documenting)
  production_runs.csv  484 runs with a baked-in root-cause story
docs/
  ARCHITECTURE.md     tool contracts, privacy model, data-flow
  DEMO_SCRIPT.md      the 2–3 minute investigation walkthrough
```

**The read-only guardrail.** Agent-supplied SQL is validated before it runs: single statement only, must start with `SELECT`/`WITH`, comments are stripped first (so `-- ; DROP` can't sneak through), and a keyword blocklist rejects any mutation, DDL, engine escape hatch (`ATTACH`, `INSTALL`, `PRAGMA`…), file reader (`read_csv`, `read_parquet`…), or external URL. Only the human's file picker registers datasets. Results are row-capped, and queries run under a time budget. It's a read-only guardrail for a hackathon demo, not a hardened sandbox — see the notes in `db.js`.

## Tech

Zero backend. Zero build step. Plain ES modules, DuckDB-WASM from jsDelivr, IBM Plex + Space Grotesk from Google Fonts. All inference runs in the user's own agent — the app just publishes a tool contract, so there are no API keys and no per-query cost.

## Roadmap

Ideas beyond this submission, in rough priority order:

- **Two-step disclosure flow** — split `requestRows` into a request stage and a separate result-fetch stage, removing the host-timeout coupling noted above.
- **Differential-privacy noise on aggregates** — layer calibrated noise on top of the hard k-anonymity floor for stronger guarantees on borderline group sizes.
- **Automated privacy-invariant tests + CI** — assert masking, k-suppression, deny-on-decline, and ledger completeness on every push.
- **Multi-agent handoff** — let a second agent (or a second analyst) pick up an in-progress investigation from its exported report, replaying the same disclosure boundary.
- **An "explain this disclosure" tool** — let the agent ask *why* a group was withheld, returning the suppression reason without revealing the suppressed data itself.
